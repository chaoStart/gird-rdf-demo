# 配电网本体设计与推理说明

本项目根据材料构建一个可在 Windows 本地运行的教学 Demo。本体承担概念和语义的定义，数据库承担事实的持久化，两者职责不同。关系数据库能够记录设备编号、容量、连接关系和开关状态，但一张设备表本身并没有声明“分段开关必然也是电力设备”。本体通过类继承、对象属性及逻辑公理表达这种知识，使推理器能够从显式事实得到隐含事实。数据库与本体并不互相排斥，RDF 数据库同样需要本体作为语义骨架。

本体采用 OWL/RDFS，以 Turtle 文件保存。二十个类覆盖设备、用户、事件和业务对象，设备下含变电站、馈线、母线、线路段、开关和配变，开关继续区分分段开关与联络开关。用户细分居民和工业用户；事件包含故障、停电及过载；业务对象包含工单与倒闸方案。所有类继承 GridEntity 上的 label 数据属性和 relatedTo 对象属性，具体设备另有容量、负荷、状态等属性。容量和负荷统一使用 kVA，避免把 kW 直接与 kVA 比较。对象属性描述电气连接、供电、上下游、所属馈线和备用馈线关系。

模式与实例分文件保存。ontology.ttl 定义词汇，demo.ttl 记录两条馈线、两个开关、三个配变与三个用户组。用户组使用 households 表示户数，避免将三个实例误报为三户。数据明确为人工模拟，Y 馈线的 currentLoad 表示聚合基线负荷，不再对 C 重复求和。示例用设备节点和无向边简化电气连接，没有完整建模 CIM Terminal、ConnectivityNode 和相别；这属于教学取舍，生产集成应另行扩展。

推理分为语义推理与运行分析。OWL RL 负责子类继承、连接对称以及上下游传递。实时开关状态不直接写成 OWL 单调公理，而在每次请求中形成场景覆盖：从在役电源出发，移除断开的开关、停运、故障和检修设备，再进行连通性遍历。只有用户的全部供电配变都不可达，才判定失电。因此 S1 断开并不必然造成下游用户停电，如果 L1 已闭合且存在备用供电路径，系统仍可判定用户带电。分析不改变数据库，也不将本次结果遗留到下一请求。

转供分析在假设联络开关闭合的网络中复算，校验失电目标是否全部恢复、备用电源是否实际接入、备用馈线容量是否足够，以及联络区域是否发生多电源并列或成环。容量与连通性满足只表示初筛通过，系统始终返回 operationally_approved=false。潮流、电压、线路热稳定、保护配合及调度规程未实现；不输出可执行操作票。故障与检修依据输入事实生效，不推断不存在的故障清除条件。

数据库提供三种运行方式。local 使用内存 RDF 图，便于复现；sparql 从配置好的独立命名图读取一次快照，失败时直接报告，不悄悄切换到模拟数据。独立导入脚本只在显式确认参数下追加 Demo 三元组，不删除原数据，不创建数据库服务。用户确认现有 Neo4j 后，本项目增加属性图适配器：以独立标签和作用域保存完整 RDF 三元组，另生成实例关系投影，供 Neo4j Browser 查看；OWL 语义仍由 Python 推理器处理。不会引入额外数据库，MySQL、Redis、MinIO、ES 暂不参与本 Demo。Neo4j 地址、版本及鉴权尚待确认，真实数据库联调不能视为完成。

对话端采用可审计的确定性意图路由，将有限中文问题映射到分析工具，并返回结构化证据。它不是通用大语言模型 Agent，多意图、设备名泛化和复杂上下文尚需后续扩展。可视化展示实例电气图及本体继承图；自动化验证同时检查正常场景与备用路径、多电源、过载及无效数据等边界。这样可以让 Demo 的每项结论有依据，同时清楚标示其工程能力范围。
